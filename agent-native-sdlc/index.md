# AI 编码的下一阶段，是重造研发系统

- Date: 2026-10-11
- Author: ByF
- URL: https://blog.baifan.site/agent-native-sdlc/
- Description: 两年 AI 研发实践的核心结论：编码提速不等于交付提速，行业数据显示交付稳定性持续承压，瓶颈已转移到评审与验证环节。下一阶段的竞争力在于重造研发系统——前置规格化、评审工程化、护栏内直接动手，以及人机分工的 Agent 原生 SDLC。

---


两年下来，团队里每个人写代码的速度都翻了几番，交付却没变快。复盘过足够多的项目之后，结论收敛成一句话：瓶颈没有消失，它从编辑器搬进了评审队列和验证流水线。这篇文章把两年摸索出的判断摊开来讲，最后一个判断是方向性的：AI 编码的下一阶段，是重造研发系统。

## 编码提速，交付没有

先承认一个反直觉的事实：AI 没有让研发整体变快，行业数据到今天都不支持。

DORA 年度报告是这个领域样本最大的工程效能研究。2024 年版（[报告发布文](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)）的回归结论：AI 采纳率每提升 25%，交付吞吐量估计下降 1.5%，交付稳定性估计下降 7.2%。2025 年版（[报告发布文](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)）样本扩到近 5,000 名从业者，吞吐量转为正相关，稳定性依旧负相关。报告把机制说得很直白：AI 加速了软件开发，而加速度会把弱点暴露在下游——没有健壮的自动测试、成熟的版本控制实践和快速反馈回路，变更量的上涨就直接转化为不稳定性。

数据边界要交代：这是横断面问卷的相关性研究，两年间吞吐量方向翻转过一次，引用该取方向而非点估计。但两个年份、两拨样本在稳定性上给出同一符号，方向够硬。

这套现象，约束理论（Goldratt，《The Goal》，1984）早给过一般解法：系统吞吐由最窄的环节决定，给非瓶颈环节提速，产出一点不变，只会堆积在制品。编码曾是软件研发里最窄的那段，AI 把它打掉了，流水线的最窄处顺位移到评审、集成、验证。这是流水线的数学，与模型能力无关。

代码库里的化石证据来自 GitClear。它 2025 年的[年度报告](https://www.gitclear.com/ai_assistant_code_quality_2025_research)分析了 2.11 亿行变更代码，结论：2024 年是 copy/paste 代码首次超过 moved（重构类）代码的年份。moved 行占比从 2020 年的 24.1% 掉到 2024 年的 9.5%，copy/paste 同期从 8.3% 升到 12.3%。2026 年的[新报告](https://www.gitclear.com/the_ai_code_quality_maintainability_gap)把曲线继续画了下去：moved 占比 2026 年上半年只剩 3.8%，跨文件函数调用自 2023 年下降 35%，开发者选择复制而非重构的概率变成五倍。重复块更直观：按 GitClear 的检测口径，含 5 行以上重复代码的提交占比，两年里涨了约十倍——每复制一段，就多一个将来改一处得同步排查全部的孪生副本。

METR 2025 年 7 月的[随机对照实验](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)让 16 位资深开源开发者在自己最熟的仓库里做 246 个真实 issue，允许用 AI 的一组实际慢了 19%——而他们事前预测能快 24%，做完还自认快了 20%，感知与实测完全倒挂。这份研究的局限（样本小、置信区间下限只到 +2%、不外推新手）作者自己列得很全。取它不为给「AI 拖慢开发」下结论，它顺手证明的是：个体对提速的体感不可靠，效能判断必须交给可测量的验证体系。

编码环节提的速，不会自动变成交付的速。评审与验证体系不重构，多出来的变更只是在下游换了个地方排队。

## Agent 越强，前置越贵

第二个判断：Agent 能力越强，对开工前那些笨功夫的要求越高。

机制藏在 METR 的归因分析里。20 个候选因素中拿到证据支持的第一条，是对 AI 有用性的过度乐观；另一条是「隐式仓库上下文」——AI 像一个新来的贡献者，代码库里大量知识从未成文：哪层抽象绕不过、哪个模块碰不得、测试覆盖到什么程度才算够。人花几年学会的分寸，Agent 拿不到，只能在交付里试错，试错成本全部落在下游。而且 Agent 能力每上一个台阶，能放心委派的任务边界就往外推一圈，触到的未成文知识就多一层。缺口不随能力增强收窄，反而被推得更宽。

前置规划的用处只有一个：把隐式标准显式化。意图写清楚、系统边界画出来、验证标准钉死，Agent 拿到的是规格；缺了这些，它拿到的是猜谜。Claude Code 官方最佳实践把工作流定成探索、规划、实现、提交四段（方法论见[Plan Mode 的拆解]({{< ref "posts/2026-06-29-claude-code-plan-mode" >}})），理由很直接：给 Agent 一个能产出通过或失败判定的东西，回路自己就闭上了。验证标准前置，执行才有锚。

Cognition（Devin 母公司）2025 年的[《Don't Build Multi-Agents》](https://cognition.com/blog/dont-build-multi-agents)把同一件事说得更极端：行动携带隐式决策，冲突的决策产出坏结果，所以上下文共享是可靠性的核心。观点文章，非实证研究，但它踩过的坑我们两年里都踩过。

任务书的写法由此变成硬规定：只陈述目标、上下文、约束与交付物形态，方法论动词一律禁止出现。这条规定是用一次报废的对照实验换来的，完整踩坑记录在[那篇 Skill 评测文]({{< ref "posts/2026-10-08-evaluating-agent-skills-first-principles" >}})里。

前置方案多扎实，Agent 交付就多靠谱。这条守则经过两年、几百个任务的检验。

## 评审必须是工程系统

生成量翻倍之后，评审只剩两条路：积压，或者放水。积压的代价是交付周期，放水的代价是稳定性，DORA 那条负相关曲线量的就是放水。开发者的态度数据同样在施压：[Stack Overflow 2025 年调查](https://survey.stackoverflow.co/2025/ai)里 46% 的受访者不信任 AI 工具的准确性，75% 因为不信任 AI 的答案而求助真人，在所有求助场景里排第一。

加人解决不了——评审专家的培养速度追不上代码生成速度。加时也解决不了——人一疲劳，标准就开始漂移。剩下一条路：把评审从依赖个人经验的英雄环节，改造成可横向扩展的工程系统。

这个系统至少三层。确定性检查前置：能跑脚本的全用脚本，lint、类型、测试、构建，退出码没有灰色地带，不占用任何人的注意力。判断固化：评审中反复出现的判断写成规则、模式和校验器，一次沉淀，处处生效。标准如一：主观维度用脱敏盲评和金标准清单兜底，不允许只给分不给据。

工业界已经跑出完整样本。Atlassian 2026 年 4 月[公开了](https://www.atlassian.com/blog/ai-at-work/developer-productivity-improved-with-rovo-dev)自研 AI 评审系统的内部评估：1,900 多个代码库、一年多的在线实验，结构化评审提示、事实性过滤、可操作性过滤三层质量门叠在一起，PR 中位周期缩短 30.8%，人类评审评论减少 35.6%。报告里还有个诚实的数字：AI 评审评论的采纳率 38.7%，仍低于人类评论的 44.45%——机器评审还没追平人，但它把人从第一道筛子里解放出来了。

## 护栏之内，离问题最近的人动手

评审一旦工程化，还有一层此前不可能的解法会被解锁：让不做全职工程师的人直接动手。

产品经理知道那个按钮该在哪个位置，设计师知道用户在哪一步流失，领域专家知道报表里哪个字段永远没人看。过去他们的路径是提需求、排期、等版本，一个两行的改动走三周。现在，权限沙盒、变更范围约束、一键回滚加上自动化校验，这些护栏把「直接改」的风险封进可控边界。离客户问题最近的人，第一次能在受控范围内自己动手做细粒度改良。

非工程师在护栏内动手，目前还没有行业口径的统计可引，这个判断来自实践观察。非工程师的产出普遍停在能跑的原型：主干逻辑对，边界情况与长期演化的部分上不去，最后一公里仍然是工程师的活。护栏解决的是「不搞坏」，不保证「足够好」。把护栏内的小改进和护栏外的系统变更混为一谈，会同时低估两者。对分工逻辑更完整的拆解在[团队分工的思考]({{< ref "posts/2026-08-03-team-roles-evolution-ai-era" >}})里，此处只补一句：护栏改变的是动手的资格，判断的稀缺没有变。

## 责任链收口于人

Agent 的能力清单逐年变长：执行、校验、重试、给出备选方案。但另一份清单纹丝不动：出事时谁来负责。

三处权威文本把这件事钉得很死。Atlassian 的评估报告写明，是否采纳建议的最终决定权完全在人；Anthropic 的[Agent 建构指南](https://www.anthropic.com/engineering/building-effective-agents)把人类评审列为方案对齐系统级需求的必要环节；DORA 2025 的总纲只有一句话——AI 不会修复团队，它放大团队已有的东西。流程是坏的，AI 让它坏得更快。

出问题的时候看得最清楚。Agent 不会为线上事故挨骂，不会为错判的需求负经济学责任，也不会在复盘会上解释当时为什么那么改。责任在人类的组织结构里流转，从未外移——意图定义、产品品质、系统架构、高风险决策，始终落在具体署名的那个人手里。

还有个注脚。METR 2026 年 2 月[宣布](https://metr.org/blog/2026-02-24-uplift-update/)放弃它的开发者提效实验：第二轮里 30% 到 50% 的开发者承认故意不提交「没有 AI 就不想做」的任务，样本系统性失真。连「如何度量人机协同」这个元问题，传统工具都开始失效。度量方法本身都要围绕 Agent 重造，何况研发系统。

## 下一阶段：把研发系统当产品重造

判断从渗透数据开始。第一阶段已经充分渗透：DORA 2025 里九成从业者在工作中使用 AI；[GitHub Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/) 统计到超过 113 万个公开仓库引入 LLM SDK，同比增长 178%。工具竞赛打了一年半，个体端的提速已经见顶，证据就是第一节那几条下游曲线。

下一阶段的主题换轴心：把研发系统本身当产品重造。需求以机器可执行的规格表达，验收标准即测试；评审由自动化流水线承载第一道，人守最终裁决；验证体系从项目附属品升级为一等公民——它是 Agent 闭环的前提；组织结构跟着调。DORA 给技术管理者的建议是把 AI 采纳当作组织转型来对待，报告同时强调，回报主要来自对平台质量、工作流与协同的战略投入。

重造后的分工清晰到可以写进职责表：人定义意图、做出决断、把控工程判断；Agent 执行推进、闭环验证、扫清交付障碍。研发系统的使命，就是把这个协同的效率推到极限。

这种量级的重排有过先例。编译器重排过「程序员」这个职业的内涵，CI/CD 重排过研发系统的拓扑，Agent 原生会是同量级的一次——演进路径的细节，此前写[从 Copilot 到 Autonomous Agent]({{< ref "posts/2026-07-03-ai-coding-tools-future-copilot-to-agent" >}})那篇时画过草图，现在进施工图阶段。

## 还没有答案的

度量是第一个黑洞。METR 的随机对照实验在个体层面尚且做得如此艰难，团队级的「AI 采纳对交付质量的净效应」至今没有可信的因果估计，我们内部两年的归因也只能做到「强相关」。第二是评审自动化的误报经济学：三层质量门本身要人维护，误报把人拉回来的成本和漏报放过缺陷的成本怎么定权重，行业里没有共识数据。第三是需求侧：产能翻倍之后，瓶颈大概率继续上移到需求定义——到时候该重造的，可能轮到产品流程本身。

第一阶段的竞赛已经跑完。第二阶段的工程，才刚开始。
