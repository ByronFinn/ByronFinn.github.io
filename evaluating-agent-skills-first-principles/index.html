在讨论 Agent 架构工程时，我们在《https://blog.baifan.site/claude-code-skills-system/》和《https://blog.baifan.site/give-ai-a-rulebook/》中解析过：Skill 本质上是给大模型按需注入的一叠行为规约。但在现实工程落地中，评定一个 Skill 是否有效，充斥着无对照的展示性偏见（Showcase Bias）：开发者写完几页文本规则，丢给 Agent 一个需求，Agent 吐出一份排版精致的代码或架构设计，开发者便截屏宣称“效果惊人”。

这种单点演示在因果推断上几乎不具备信噪比。无法确定这份高质量交付物究竟源于文本规约对模型动作的定向约束，还是单纯吃到了底层基础模型自身的高水平推理红利。

度量一个 Skill 的真实价值，必须将质量增量与资源消耗独立核算。我们在维护工程化指令集 dev-skills 时落地了一套度量管线，其因果推断逻辑通用于各类垂直领域的 Agent 技能评估。

一、 因果链拆解与核心核算公式
#

1. 技能许诺的因果链
#

评估一项技术，首先审视其许诺的因果关系。Skill 的核心主张依赖一条脆弱的串联因果链：

$$\text{注入技能文本} \xrightarrow{(1)} \text{模型内化规约} \xrightarrow{(2)} \text{执行行为定向改变} \xrightarrow{(3)} \text{最终交付物质量跃迁}$$

这条因果链在实际执行中极易断裂：

  • 环节 (1) 断裂：长上下文注意力衰减，注入的技能文本被模型注意力机制直接略过。
  • 环节 (2) 断裂：模型正确解析了文本规约，但执行时依然沿袭预训练习惯选择捷径。例如规约明确要求“先编写失败测试”，模型依然先行编写业务代码。
  • 环节 (3) 断裂：行为发生了定向改变（例如增加了 4 轮交互澄清），但最终交付物质量相比直接生成并无统计学上的显著提升。
  • 出现负向收益：模型严格执行了规约动作，产出质量微弱改善 1%，却额外占用了 15,000 Token 的上下文，并引入了多轮冗余往返时延。

评测系统的职责是在这条因果链的各个节点设置探针，逐环验证状态转换，杜绝仅凭最终产物的主观印象做定性评估。

2. 双账本独立核算：拒绝合成单一分数
#

判定挂载技能是否具备净收益，终极命题在于：

相较于完全不挂载该技能、仅凭自身能力做决定的原生基线模型，挂载该技能后带来了多少可归因的净提升？

核心评估形态是一个差值算式，且必须维持双账本独立核算：

$$\text{净收益} = \Delta \text{质量} - \Delta \text{成本}$$
  • $\Delta \text{质量}$（收益项）：由确定性自动化检查（Exit Code 0/1）与主观双盲对调打分差值组成。
  • $\Delta \text{成本}$（开销项）：包含静态注入开销（技能正文及其外部依赖闭包的 Token 总量）与动态执行开销（API 往返轮次、工具调用频次、端到端时延）。

将质量与成本强行折算为一个“综合性价比得分”会掩盖业务权衡。在 dev-skills 的架构安全质询技能 grill 中，一次评审多消耗 30,000 Token，若能拦截高并发死锁缺陷，在分布式容灾场景下该成本完全可以忽略；反之，若一个 Commit 规范化技能每次占用 8,000 Token，在日均触发数千次的 CI 流程中即构成资源浪费。评测体系应将质量差值与成本差值全景并列，由具体业务场景决策折算边界。

实施配对实验需遵循三项基准：

  1. 控制唯一自变量：两臂使用完全相同的底层模型版本、系统提示词基底、解码温度（Temperature）与随机种子。唯一的区别在于上下文中是否挂载该技能文件及其依赖。
  2. 消除跨任务方差：严禁跨越不同任务进行分数绝对加总。所有胜负判定与打分必须在同一个任务内部的双臂之间相对展开。
  3. 最小分析单元（Skill $\times$ Task）：技能库内部存在非均质性。一个包含十项规范的技能包，往往由少数强有效规则、大量平庸规则与个别负优化规则混合而成。必须以“技能 $\times$ 任务”切片为最小单元，逐一产出三类判定：有证据支持的优势（Superior）、无显著差异（Neutral）与劣势负优化（Inferior）。

三、 七项核心设计原则与反面模式
#

评测方案的有效性取决于测量仪器本身的系统性稳定性。以下七项设计原则分别对应行业评测中常见的失真陷阱：

原则 1：对照组无处理（严防任务书污染）
#

  • 反面模式：在评测代码重构技能时，任务描述写为：“请先梳理代码坏味道清单，逐一给出方案，确保向后兼容，最后完成修改”。这直接将技能内部要求的过程方法泄漏给基线臂，导致两臂人为打平。
  • 设计规约：任务书仅允许陈述目标（What）、业务上下文（Context）、硬性约束（Constraints）与交付物形态（Deliverables）。凡能与技能规约条文对应的思考动作与推导方法，一律禁止出现在初始任务书中。

原则 2：保障差异具备触发空间（交互可实现性）
#

  • 反面模式：许多技能的价值在于主动交互与逆向澄清。若将评测置于单轮离线批处理脚本中，技能臂缺乏交互对象，只能自问自答或跳过澄清环节。
  • 设计规约：针对包含交互规约的技能，测试环境必须配备受控模拟器（Client Simulator）。模拟器维护独立约束档案，并在双臂提出相同问题时通过哈希缓存返回完全一致的回答，隔离人际交互噪声。

原则 3：校准任务难度基准（规避天花板效应）
#

  • 反面模式：使用过于简单的常规任务进行测试。现代基模型在无约束状态下即可达到 90% 以上通过率，导致两臂同时触顶，测量仪器丧失区分度。
  • 设计规约：将任务难度校准在 40%–70% 的基线通过率区间。在正式评测前，由独立测试员盲测任务。若未挂载技能的基线臂能够通过 80% 以上，该任务判定为失效，必须重新注入带有干扰性的虚假根因（Distractor）或隐式边界条件。

原则 4：建立三层证据阶梯（确定性校验优先于模型盲评）
#

  • 反面模式：直接依赖通用大模型作为裁判（LLM-as-a-Judge）对两臂交付物打分。该方式会引入裁判模型固有的位置偏差、字数冗长偏好与排版审美偏好。
  • 设计规约：构建分层判定机制：
    1. L1 确定性检查（权重最高，零模型自由度）：执行隐藏测试用例、静态检查工具（Linters）与自动化验收脚本，仅以退出状态码（Exit Code 0/1）为裁决标准。
    2. L2 金标准清单比对（Gold-standard Checklist）：人工预设核心事实清单与陷阱排查表，裁判仅做布尔命中核验（Boolean Hit/Miss），禁止进行开放式打分。
    3. L3 双盲对调审计（主观维度）：交付物彻底脱敏，移除工具链调用元数据；两名独立评审员交叉打分，评审顺序强制对调；打分必须引用原文标出至少 2 处具体硬伤。

原则 5：归因可分离（区分逻辑缺陷与遵循度失效）
#

  • 反面模式：当技能臂输出落后时，直接归咎于技能规约逻辑错误。日志显示模型由于注意力分散，根本未执行规约要求的检查动作。
  • 设计规约：将指令遵循度（Compliance）与交付物最终质量（Outcome）分流统计：
    • 审计执行轨迹（Trace）：技能臂是否按规约完成了中间状态分析或特定测试时序。
    • 遵循度低下反映提示词引导性缺陷或上下文超载；遵循度充分但产出质量依旧落后于基线，方可确诊为规约逻辑本身的负优化。
    • 设立内容哈希（MD5）熔断门：若两臂最终交付物的哈希值完全一致，说明任务存在单一确定解，该测试样本直接废弃。

原则 6：成本透明入账
#

  • 设计规约：
    • 静态成本精确计提：技能文件自身及其引用的全部外部文档 Token 数，按全量闭包求和，明确记录于报告中。
    • 动态运行开销全景记录：多步规划型技能通常带来更多交互轮次与思考耗时。将 API 轮次、工具调用量与运行耗时作为独立维度记录，供工程团队权衡边际收益。

原则 7：实验预注册（固化判定标准）
#

  • 反面模式：在观测到实验数据后动态调整指标权重，通过放大特定维度强行得出技能胜出的结论。
  • 设计规约：借用预注册机制（Pre-registration），在运行测试前通过版本控制（Git Commit）冻结评测标准。明确硬性胜出门槛（如：确定性验证不劣于基线的前提下，盲评均分领先 $\ge 10%$）。实验完成后禁止追溯修改裁量逻辑。

任务矩阵设计的核心：定向触发行为模式
#

评测任务必须针对技能意图纠正的不良行为模式进行特异性设计。以 dev-skills 体系为例：

技能类别与示例核心考察的行为差异点任务埋设方法裁决依据
交互澄清类
think		拒绝默认假设，主动发起逆向提问收敛需求边界。任务书给出表面完备但暗含关键冲突的需求；真实边界仅存在于模拟器档案中。模拟器隐蔽约束的挖掘率与有效交互轮次。
架构质询类
grill		穿透表层合规方案，指出深层架构隐患。提供无 Lint 报错的完整设计，预埋分布式并发时序竞争与资源泄漏点。金标准预置缺陷清单召回率，剔除细枝末节的无病呻吟（Nitpicks）。
严谨实现类
tdd		落实测试先行流程，杜绝先写实现后补假测试。算法逻辑具备复杂的边界契约，直接实现极易遗漏极端情况。过程时序审计（Git 提交时间线与文件修改次序） + 隐藏测试套件退出码。
研究调研类
research		基于权威语料作答，杜绝基于参数权重的幻觉外推。针对特定开源库发生破坏性变更（Breaking Change）的最新 API 提问。关键事实核对、版本陷阱避坑率与引述来源的一致性。

五、 评测报告审阅三步法
#

技术团队在评估外部或内部技能评测报告时，可通过以下步骤校验其有效性：

1. 任务书 Diff 检查
#

比对被测技能的规约文档与评测任务书。若任务书中包含“请仔细检查边界情况”、“请优先考虑向后兼容”等提示性语言，表明基线已被污染，其宣称的质量增益不具备因果有效性。

2. 区分两种平局（True Tie 与 Winner Disagreement）
#

当报告显示双臂打平时，需核验底层分项数据：

  • 真平局（True Tie）：双臂在确定性检查上表现一致，且独立双评委在盲评中均给出等价判定。表明针对当前任务难度，基模型能力已足以覆盖需求，技能无增量收益。
  • 评委分歧（Winner Disagreement）：评委 A 判甲胜，评委 B 判乙胜。表明任务标准缺乏客观界定，结果受主观解释干扰，不可简单归为平局，应标记为“证据不足”。

3. 核算边际资源代价
#

计算技能臂取得质量优势所付出的真实开销。若某项技能为了在极端边界案例上获取边际提升，常态化注入 15,000 Token 并显著拉长端到端时延，在日常高频调用场景中，此类技能应当被精简或移出常驻上下文。

结语

在以 Agent 为核心的工程系统中，编写 Skill 极易产生掌控感：自然语言不存在编译期报错，写下几段守则，系统便似乎获得了专业能力。
